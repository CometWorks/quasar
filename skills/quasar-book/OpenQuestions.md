# Open questions

Things the Quasar code leaves unclear, places where the repository's `Docs/` and the code disagree, and features the docs describe that the code doesn't do yet. Found while writing this handbook. Where docs and code disagree, the pages follow the code.

Don't answer these from the handbook. Say the behavior isn't documented, or check the current code. Maintainers: resolve an item in Quasar or its docs, then update the page and remove the item here.

## Installing and running

Pages: [Install on Linux](InstallLinux.md), [Install on Windows](InstallWindows.md), [Docker](Docker.md).

- `uninstall.sh --system` without `--install-dir` sets the install dir to `/opt/quasar`, while `install.sh --system` from a release archive installs in place (script folder). `sudo ./uninstall.sh --system --purge` from such an install targets `/opt/quasar`, not the real install. Bug? Files: `uninstall.sh`, `install.sh`, `Docs/LinuxDeploymentAndUpdates.md`.
- The release programs are self-contained single-file builds, yet `install.sh` still requires `Microsoft.NETCore.App` and `Microsoft.AspNetCore.App` 10 for a packaged install. Magnetar needs `Microsoft.NETCore.App` 10, and on Linux `Quasar` needs the system ICU that the runtime packages bring (a foreground run on a host without ICU stops at once, SE1-0285). Does anything still need `Microsoft.AspNetCore.App`? `install.ps1` no longer checks for any .NET; does Magnetar on Windows need a runtime the admin must install? Files: `install.sh`, `scripts/install.ps1`, `Quasar/Quasar.csproj`.
- `Install.cmd` runs `install-gui.ps1` with `-ExecutionPolicy Bypass`, but running `.\install.ps1` or `.\uninstall.ps1` by hand from a downloaded zip still meets the execution policy and Mark of the Web. Is `Unblock-File` or `-ExecutionPolicy Bypass` needed in practice? Files: `scripts/Install.cmd`, `scripts/readme-install-windows.md`, `Docs/Installation.md`.
- Docker image is published only on pushes to `main` that create a full release; tag pushes (`v<version>`) also create full releases but no image. Docs say "for every full release". Files: `.github/workflows/release.yml`, `Docs/Docker.md`.
- Docker: **Shutdown Quasar** stops the worker (exit 0) but Compose uses `restart: unless-stopped`, so Docker likely starts it again. What is the intended container behavior of Shutdown Quasar? Files: `docker-compose.yml`, `Quasar/Services/QuasarShutdownService.cs`.
- Docker: `QUASAR_PUBLIC_BASE_URL` becomes `WebServiceOptions.BaseUrl`, which Quasar also passes to managed servers as `QUASAR_BASE_URL`. Is it safe to set it to a public reverse-proxy URL, or would agents then connect through the proxy? Files: `.env.example`, `Quasar/Services/WebServiceOptions.cs`, `Quasar/Services/DedicatedServerSupervisor.cs`.
- Docker: `QUASAR_UPDATES_ENABLED=false` also stops `ClusterReleaseMonitor`. Do UI plugin auto-updates (`QUASAR_UPDATES_AUTO_UPDATE_UI_PLUGINS`, listed in `.env.example`) and cluster package updates work in the container? Files: `.env.example`, `Quasar/Services/ClusterReleaseMonitor.cs`, `Quasar/Services/Plugins/QuasarUiPluginHubCatalogService.cs`.
- Docker image runs as root (no `USER`), but `Docs/Docker.md` talks about "permissions for the container's service account" for the diagnostics folder. Which account is meant? Files: `Dockerfile`, `Docs/Docker.md`.
- Docker backup: should the container be stopped before copying `quasar-data` (open saves, JSON files)? Docs say only "back up as one unit". File: `Docs/Docker.md`.
- Firewall: which per-server ports must be opened for players (game port UDP only, or also the Steam port game+1000)? No doc or script says. Files: `Quasar/Services/DedicatedServerRuntimePreparer.cs`.
- New installations and the 1.5 gate: `install.sh` and `install.ps1` run `check-upgrade-path` against an empty data directory too, so a brand-new 1.5 install is refused until 1.4.1 has run there. The docs say "Start with 1.4.1 for a new installation that will move to 1.5". Is this meant to stay for every later release, or will fresh installs of 1.5 and later get a path without 1.4.1? Files: `Shared/Updates/QuasarUpgradePath.cs`, `install.sh`, `scripts/install.ps1`, `Docs/ReleaseNotes1.5.md`.
- Docker and the 1.5 gate: `Program.Main` checks the 1.4.1 receipt on `/data` too, and only a 1.4.1 container writes it (`QuasarApplicationEntry.ConfirmManualUpdate`). A 1.5 image on a new or pre-1.4.1 `quasar-data` volume should therefore exit with code 3 at once and, with `restart: unless-stopped`, loop. `Docs/Docker.md` and `Docs/ReleaseNotes1.5.md` don't mention containers. Is a new Docker deployment meant to run the 1.4.1 image first, and is that image published? Docker.md states the code behavior; a live run would confirm it. Files: `Quasar/Program.cs`, `Quasar/Services/QuasarApplicationEntry.cs`, `Shared/Updates/QuasarUpgradePath.cs`, `Dockerfile`.
- `uninstall.ps1 -Purge` deletes only the application folder. A separate data folder, such as the guided default `%ProgramData%\Quasar`, stays, while the final message says data is retained "unless -Purge was supplied". Intended? Files: `scripts/uninstall.ps1`, `scripts/install-gui.ps1`.
- The guided Linux installer installs system services running as the desktop user, while `./install.sh` defaults to user services, and it looks for an existing install only in `~/.local/share/Quasar` or the package folder. An existing user-service install elsewhere (for example in place in `~/Quasar`) would get a second, system-scoped install. Intended? Files: `scripts/install-gui.sh`, `install.sh`.

## Servers and config profiles

Pages: [Servers](Servers.md), [Config profiles](ConfigProfiles.md).

- Exits the agent doesn't report: with current Magnetar the DS's own exit and a plugin `SaveAndQuit` reach Quasar as an admin stop, so the goal goes Off, and an exit before Running is a failed start. An exit the agent doesn't see (agent not loaded, older Magnetar) still restarts when `RestartOnCrash` is on and the goal is On, whatever the exit code. With `RestartOnCrash` off, exit code 0 ends in `Stopped` and the reconcile loop starts it again because the goal is still On. `Docs/StateMachines/DedicatedServerLifecycle.md` says "Running -> Stopped: clean exit, not requested". Is that intended? (`Quasar/Services/DedicatedServerSupervisor.cs` HandleProcessExitedAsync + ReconcileAsync, `Quasar.Agent/SupervisedLifecycle.cs`, `Docs/StateMachines/DedicatedServerLifecycle.md`)
- "Rendered DS config path" (`ConfigFilePath`) is described in the editor as where Quasar writes `SpaceEngineers-Dedicated.cfg`, but `PrepareRuntimeConfigAsync` only reads it as a source and always writes to `<DS app-data>/SpaceEngineers-Dedicated.cfg` (also what Magnetar gets via `-path`). Which is intended? Left out of the pages. (`Quasar/Services/DedicatedServerRuntimePreparer.cs`, `Quasar/Components/Pages/ServerEditorDialog.razor`)
- In-game bans/admin promotions: Quasar replaces `Administrators`, `Reserved`, `Banned` in the DS cfg from the profile on every start. Does the DS persist in-game bans (or agent `BanPlayer`) into that cfg, so they are lost at the next start? The page states only the replacement fact and tells admins to put bans in the profile. (`DedicatedServerRuntimePreparer.cs` ApplyConfigProfile/UpsertArray, `Quasar.Agent/GameBridge.cs`)
- ConfigProfileChanges.md says "Applied changes go live unless marked restart-required". No restart-required marking or live push of profile changes exists in code; profiles apply only at start. The doc should be corrected (or the feature is planned). (`Docs/StateMachines/ConfigProfileChanges.md`, `Docs/QuasarArchitecture.md` Config flow)
- Architecture doc says "Lifecycle action buttons are hidden during transitionary states, except Stop while Starting"; the UI actually shows Kill (not Stop) while Starting/Restarting. Doc drift. (`Docs/QuasarArchitecture.md` Process Supervision, `Quasar/Components/Dashboard/ServerCard.razor`)
- `ServersPageDialog.razor` is not opened anywhere; dead component? (`Quasar/Components/Pages/ServersPageDialog.razor`)
- Default `MinimumSimulationProgressScore` differs: model default 0.1, UI-created servers 0.05 (`CreateBlank`). Imported servers get which? Intentional? (`Quasar/Models/DedicatedServerDefinition.cs`, `Quasar/Services/ServerManagementActions.cs`)
- `RecycleAfterUptimeHours` (health recycle) and per-server `AvoidSimultaneousScheduledRestarts` exist in `server.json` but have no UI; the supervisor uses the global option, not the per-server field. Left undocumented. (`DedicatedServerDefinition.cs`, `DedicatedServerSupervisor.cs` CanRunPlannedRestart)
- The editor port check covers only the game port; derived Steam (+1000) and Remote API (+2000) ports of other servers are not validated. Worth a validation? (`ServerEditorDialog.razor` ValidatePortField)
- `Create From Template` in the server editor creates the save folder immediately, before the server definition is saved; canceling the editor leaves the folder. Intended? (`ServerEditorDialog.razor` CreateWorldSaveFromTemplateAsync)

The use case Servers.md gives (servers without Steam access that fail with "Unable to download mods") comes from PR #233, not from the UI or docs. Should the editor say so? (`Quasar/Components/Pages/ServerEditorDialog.razor`)

- Possible bug: in a scheduled Servers/Worlds rule, one failing server (e.g. no world selected) aborts the whole run before `UpdateLastBackupAsync`, so the rule retries every minute and re-creates backups of the servers before the failing one each time (pruned to N). Page documents the observed behavior. File: Quasar/Services/Backup/AutomaticBackupService.cs (PerformBackupAsync).
- Automatic (scheduled) backup failures are only logged; no notification or UI indicator for scheduled-rule failures (only queued/manual jobs raise QueuedBackupCompleted). Intended? File: AutomaticBackupService.cs.
- `QUASAR_COORDINATED_UPDATES` is still set by the legacy Bootstrap launcher, but nothing reads it any more; only `QUASAR_COORDINATED_ROLLBACKS` gates the legacy worker-only rollback. Leftover? Files: Quasar.Bootstrap/Program.cs, Quasar/Services/Updates/QuasarUpdateService.cs.
- On native installs `CheckNowAsync` builds the launcher candidate from the complete package, so a newer release raises both "Quasar update available" and "Quasar launcher update available" for the same version. Intended, or should the launcher notice be legacy-only? Files: Quasar/Services/Updates/QuasarUpdateService.cs (CheckNowAsync), Quasar/Services/Updates/UpdateNotice.cs.
- `Quasar update` exits with code 6 when the operation is still pending. How long the command waits before giving up is not documented. File: Quasar.Bootstrap/UpdateCli.cs.
